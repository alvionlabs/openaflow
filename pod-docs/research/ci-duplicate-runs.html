Avoiding duplicate CI runs when promoting pod-staging to main

Generated 2026-11-22 · standard depth · 2 searches · 23 pages read. Full report with all sources: ci-duplicate-runs.md. Items marked (inference) or (own idea) are not from a page.

Assumptions: repo plan is unknown (personal or Free/Team org); nobody pushes straight to main; "duplicate" = push run on pod-staging plus pull_request run on the staging PR into main.

Recommendation

Drop push, keep both pull_request gates (own idea)

on:
  pull_request:
    branches: [pod-staging, main]
concurrency:
  group: pod-ci-${{ github.event.pull_request.number }}
  cancel-in-progress: true

Gives up: no run after a merge into pod-staging (merge skew unseen until the next PR); no run on main after promotion. Matches your kept decision: CI at sprint end into pod-staging and on the staging PR into main.

Alternative: keep push: [pod-staging], remove main from pull_request. The staging PR shows the push run on the same head SHA (adamj.eu). Gives up the merge-with-main run.

What each choice loses

Drop push (staging)

Lose the post-merge run. pull_request tests the merge ref at PR time and does not run with merge conflicts (docs).

Drop pull_request (main)

Lose the run on the merge with main. Push run tests the head SHA only. Same tree if main is an ancestor (inference).

Concurrency

Different events use different default refs; docs do not address cross-event groups. A shared SHA key only helps if runs overlap (inference).

Required checks later

Skipped workflow: checks stay Pending and block merging. Skipped job via if: Success (docs). Use one always-run aggregate job.

CI after merge

Only a push run finds two PRs that pass alone but break together; merge queue prevents it by testing combined state (blog). Low risk if only the sprint PR enters staging (inference).
