**Assumptions:**
- Angle is `building` only: mechanics and best practices, not a survey of competing products.
- claude-pod is a normal Claude Code plugin (a `.claude-plugin/plugin.json` plus `skills/`, `agents/`, `hooks/`). I did not read the claude-pod repo.
- OpenAFlow starts `claude` itself in a pty, so it can set CLI flags and environment variables per session.
- "Build time" means the OpenAFlow release build (electron-builder run, local or CI).

## Gaps and angles

- **Plugin name collision.** `claude plugin validate` errors on any plugin name that starts with `claude-`. The error reads `Plugin name "<name>" is reserved`. The docs also say `claude plugin init` and `claude plugin tag` refuse such a name, but "Claude Code still installs and loads" it. If the manifest name of claude-pod starts with `claude-`, validation fails in CI (and `--strict` does not help). I did not check claude-pod's manifest. — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- **`CLAUDE_PLUGIN_ROOT` is read-only in practice.** It points at the version directory, and it changes on update. The docs say to keep durable files in `CLAUDE_PLUGIN_DATA`. For a `--plugin-dir` plugin the root is the bundled folder, which sits in the app install dir (may be read-only; for AppImage it is a read-only mount, not verified). So the plugin must never write there. — [manifest reference](https://code.claude.com/docs/en/plugins-reference), [loading](https://code.claude.com/docs/en/plugins/loading.md)
- **Env vars do not reach every place.** `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA`, `CLAUDE_PROJECT_DIR` and `CLAUDE_PLUGIN_OPTION_<KEY>` go to hook processes and MCP/LSP stdio servers. They are not set in the Bash tool, in the main session, or in subagents. In skill and agent Markdown, write `${CLAUDE_PLUGIN_ROOT}` and Claude Code substitutes it inline. — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- **No documented "host overrides plugin file" layer.** The plugin docs describe loading a directory, not merging a user layer on top. `--plugin-dir` of a same-named plugin replaces the other one entirely (whole plugin, not per file). — [loading](https://code.claude.com/docs/en/plugins/loading.md)
- **Per-file user edits conflict with a version bump.** Copier's model needs git and a stored answers file in the user's project. A desktop app copy in a user folder has neither by default. — [Copier updating](https://copier.readthedocs.io/en/stable/updating/)
- **npm git-URL route has an install-time side effect.** Install scripts run for a git dependency that defines them. Claude Code's own `npm` plugin source forbids tarball links on github.com, even release downloads, and refuses git addresses as `package`. That rule applies to Claude Code's source fetch, not to your own build script. — [npm docs](https://docs.npmjs.com/cli/v10/configuring-npm/package-json#git-urls-as-dependencies), [marketplace-reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md)
- **Asset digest backfill unknown.** The GitHub post does not say whether old assets have a digest. A build script should not depend on the API field alone. — [GitHub changelog](https://github.blog/changelog/2025-06-03-releases-now-expose-digests-for-release-assets/)

## Best practices

- **Bundle the plugin as a plain folder through `extraResources`, not inside asar.** The docs say to use it for "data files that need to be accessible at runtime" and that these files sit outside `app.asar`. Claude Code (a separate process) needs a real path, and it cannot read inside asar. (The second half is my inference; the docs say files outside asar are real files.) — [electron-builder contents](https://www.electron.build/docs/contents)
- **Resolve the path with `process.resourcesPath` when packaged, and a repo path in dev.** Then pass it as `claude --plugin-dir <path>`. Claude Code loads it in place, so there is no install step and no network. — [electron-builder contents](https://www.electron.build/docs/contents), [loading](https://code.claude.com/docs/en/plugins/loading.md)
- **Prefer `CLAUDE_CODE_PLUGIN_DIRS` or `--plugin-dir` per session over a marketplace install.** `--plugin-dir` is "for that session only", needs no settings write, and cannot be changed by a stale cache. The loading doc lists `@inline` plugins as session-only. — [loading](https://code.claude.com/docs/en/plugins/loading.md)
- **Pin by tag and by content hash.** Marketplace sources accept `ref` plus a full `sha`. When both are set, Claude Code checks out `sha`, so a moved or deleted tag cannot change what you get. `archive` sources accept `sha256`, and Claude Code refuses a mismatching download. The same idea applies to your own build script. — [marketplace-reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md)
- **Build script pattern (download by tag, verify SHA-256).** Steps: (1) read `{repo, tag, sha256}` from one committed file; (2) download the release asset or the tag tarball over HTTPS; (3) hash it and compare with the committed `sha256`; (4) unpack into a build folder; (5) point `extraResources.from` at that folder. The committed hash means a bump is a visible diff in review. GitHub's asset digest can supply the expected value at bump time. I did not find a published reference script. — [GitHub changelog](https://github.blog/changelog/2025-06-03-releases-now-expose-digests-for-release-assets/), [electron-builder contents](https://www.electron.build/docs/contents)
- **Submodule pins a SHA, not a tag.** `git submodule update` checks out the pinned commit (detached HEAD). A plain clone leaves the folder empty, so CI needs `--recurse-submodules` or `git submodule update --init`. — [Pro Git](https://git-scm.com/book/en/v2/Git-Tools-Submodules)
- **Run `claude plugin validate <dir> --strict` in OpenAFlow CI on the pinned plugin.** It catches bad paths, unknown fields, and a missing `version`. — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- **Set `version` in the plugin manifest on each tagged release.** A manifest `version` pins the version; without it the version comes from the commit SHA. This matters only for the marketplace path, but it keeps both paths in step. — [loading](https://code.claude.com/docs/en/plugins/loading.md)
- **Keep plugin writes out of `CLAUDE_PLUGIN_ROOT`.** Put caches and generated files in `CLAUDE_PLUGIN_DATA`, or in the state folder in the user's project. — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- **Rename the state folder with an env var that beats a default, and an explicit override above that.** Prior art:
  - Git: `GIT_DIR` "specifies a path to use instead of the default `.git`" and turns off the upward search. `--git-dir` sets the same value. Without it, Git walks up parents looking for `.git`. — [git](https://git-scm.com/docs/git#_git_commits)
  - Cargo: `CARGO_HOME` overrides `$HOME/.cargo`. Each config key has an env var form, such as `CARGO_BUILD_TARGET_DIR` for `build.target-dir`. — [Cargo env vars](https://doc.rust-lang.org/cargo/reference/environment-variables.html)
  - Claude Code: `CLAUDE_CONFIG_DIR` is used as a path variable; project and local settings cannot set it (so it is a host/user-level knob). I did not find its full entry (page truncated). — [env-vars](https://code.claude.com/docs/en/env-vars)
- **Use `userConfig` for plugin knobs.** A plugin can declare a `directory`-type option with a `default`. Claude Code exports it as `CLAUDE_PLUGIN_OPTION_<KEY>` to hooks and substitutes `${user_config.KEY}` into skill and agent content (non-sensitive values only). Whether the prompt and substitution apply to a `--plugin-dir` plugin, and whether a host can pre-set the value, I did not find: `no evidence found`. — [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- **Ship a migration step for an old name.** Copier runs `_migrations` only on update, each with a `version` bound (`new >= declared > old`), in order, `before` or `after`. This is the pattern for "if `pod-docs/` exists and the new folder does not, rename it once". I did not find a CLI tool whose docs describe handling an old state-folder name; `no evidence found`. — [Copier configuring](https://copier.readthedocs.io/en/stable/configuring/)
- **For editable defaults, protect user edits by file class.** Copier has `_skip_if_exists` (copy once, never overwrite, recreate if missing), `_exclude` (never render), and a conflict mode (`inline` markers or `.rej`). It tells users "NEVER EDIT" the answers file. It needs git and tags on the template side, and a git repo with a clean tree on the user side. — [Copier configuring](https://copier.readthedocs.io/en/stable/configuring/), [Copier updating](https://copier.readthedocs.io/en/stable/updating/)

## Ideas to consider

All ideas are mine unless a link follows `grows from`.

- **Load the bundled plugin with `--plugin-dir` from `process.resourcesPath`, one resolver function.** Keep the path lookup in one module, so a later "user workflow folder" only changes that function. — grows from [loading](https://code.claude.com/docs/en/plugins/loading.md), [electron-builder](https://www.electron.build/docs/contents) (the seam itself is my own idea)
- **Seam: pass the workflow dir as an ordered list.** `CLAUDE_CODE_PLUGIN_DIRS` and repeated flags let a user plugin load next to the bundled one. Because a same-named plugin replaces the other whole, a user "replace" is just a different folder with the same manifest name. (The list and the same-name rule are in the docs; the seam design is my own.) — grows from [loading](https://code.claude.com/docs/en/plugins/loading.md)
- **Download-at-build script with a committed lock file** (`workflow.lock.json`: repo, tag, sha, sha256). `pnpm bump-workflow <tag>` rewrites it and prints the release-asset digest to compare. Fits "update is a hand bump". — grows from [GitHub changelog](https://github.blog/changelog/2025-06-03-releases-now-expose-digests-for-release-assets/) (script is my own idea)
- **Expose the state folder name as one env var from the host** (name it for the workflow, e.g. a `POD_*` variable; naming is yours) and read it in hooks and scripts with the default `pod-docs` when unset. Host-set env vars inherit to child processes in general (my inference); the docs only say which Claude Code variables reach which components. Skills cannot read env vars, so skill text must refer to the folder some other way, such as `${user_config.KEY}` (unverified for `--plugin-dir`). (own idea)
- **Rename on first run, not on every run.** Marker-file discovery: if the new folder is absent and the old one exists, ask once, then move it (git-style: walk up from cwd looking for a marker, with an env var that skips the search). — grows from [git](https://git-scm.com/docs/git#_git_commits) (own adaptation)
- **Editable default: read-only bundled plugin + user override plugin, no copy.** Because `--plugin-dir` loads in place and replaces by manifest name, "reset to default" is "stop passing the user folder". No merge is needed until you want partial overrides. (own idea, from the load rules in [loading](https://code.claude.com/docs/en/plugins/loading.md))
- **If you later copy on first run, store the base version.** Write a small manifest next to the copy (`{base: "v1.2.0", files: {path: hash}}`). On update, a file whose hash still equals the stored one is replaced silently; a changed file gets a conflict choice. This is a light version of Copier's diff model without needing git. — grows from [Copier updating](https://copier.readthedocs.io/en/stable/updating/) (own simplification)
- **CI gate:** run `claude plugin validate <bundled dir> --strict` and check that the packaged app contains the folder. — grows from [manifest reference](https://code.claude.com/docs/en/plugins-reference)

## Questions for the plan

- **What is the plugin manifest `name`, and does it start with `claude-`?** — why it matters: `claude plugin validate` errors on names starting with `claude-`; Claude Code still loads them, but a `--strict` CI gate would fail and the name decides the `@inline` id and namespace (`<name>:<skill>`). — options: keep the name and skip the validator error / rename the plugin (skills become `<new>:<skill>`) / set the manifest name different from the repo name.
- **Bundle by submodule, build-time download, or npm git URL?** — why it matters: submodule pins a SHA and needs an init step in CI; download pins a tag plus a SHA-256 you commit, no git needed; npm git URL pins a commit-ish but may run install scripts. All three end as a folder for `extraResources`. — options: A submodule / B download tag tarball + committed SHA-256 / C npm `github:` dependency.
- **Does the state-folder name get passed by env var, plugin `userConfig`, or a plugin-side config file?** — why it matters: skills and agents cannot read environment variables, only hooks and MCP/LSP processes get them; `userConfig` values reach skill text by substitution, but I found no evidence that this works under `--plugin-dir` or that a host can preset it. — options: env var for hooks + `userConfig` for skills / a config file in the user's project read by every script / hard-code `.openaflow/` in a claude-pod release and drop the old name.
- **What happens to an existing `pod-docs/`?** — why it matters: no tool in my sources documents old-name handling; Copier's `_migrations` is the only versioned pattern I found. — options: auto-detect and offer a one-time move / read both names, write the new one / leave the old name and let users opt in.
- **Does the user edit files in place, or add a second plugin that overrides?** — why it matters: in-place edits need a merge story (Copier-style); a second plugin of the same manifest name replaces the bundled one whole with no merge. — options: replace-whole-plugin only (v1) / copy-on-first-run with base hashes / per-file override layer (needs OpenAFlow code, not a Claude Code feature, as far as I found).
- **Is the bundled folder writable at run time on all targets?** — why it matters: the plugin must not write to `CLAUDE_PLUGIN_ROOT`; resources dirs can be read-only on some installs (not verified). — options: forbid plugin writes outside the user project and `CLAUDE_PLUGIN_DATA` / copy to a user data dir on each version change.
