# Actions

## What it is

Board actions change something outside the board: merge a PR that waits on you (a handed-back wave PR, a reviewed fix PR, or the final plan PR), append your answer to a queue entry that waits on you, and resume a run with `continue` or `go` (see [resume.md](resume.md)). Every merge, answer, and resume request that passes its checks goes in the action log, and so does each repo removed from the board (Remove repo, [server.md](server.md)) and each run's port claim forgotten (Forget run, [server.md](server.md)). A hosted session's New session, Resume (`POST /api/actions/resume-session`), and Dismiss log too ([hosted-sessions.md](hosted-sessions.md)), and so do Set up (create a repo's `.openaflow/`) and Use (a workflow's `version`). Server side: `packages/server/src` (the action, answer, queue-writer, and setup-routes modules); the routes sit behind the action guard ([server.md](server.md)). The screens are in [runs-and-pipeline.md](runs-and-pipeline.md).

## How it works

- **Target from the Board, never from the body.** A request names `repoId` and a PR number or a queue line; the server looks both up on the current Board. A PR must be in the model's `waitingPrs`, an entry must be `isAnswerable`, else `404 not waiting on you`. No `gh` command or file write runs before the checks pass. One merge per repo and PR, and one answer per repo, at a time (`409`).
- **Merge preview:** `gh pr view` gives title, head sha, mergeability, and checks for the confirm step.
- **Merge:** a fresh read first. A failed read → `failed`, no merge. A head that moved since the confirm → `stale`, no merge. Else exactly `gh pr merge <url> --merge --match-head-commit <sha>` (merge commit; never `--admin`, `--auto`, `--squash`, or `--delete-branch`), then a re-read decides the result:
  - `merged` only when GitHub says `MERGED`; `auto-merge` when auto-merge is on; `queued` only when GraphQL shows a merge-queue entry.
  - `unconfirmed` when the call succeeded but GitHub doesn't show a result yet; `failed` with gh's trimmed stderr, or `PR is closed`.
- **Answer:** the text is cleaned (control characters dropped, whitespace folded to one line, at most 2000 characters, no `**Resolution:**` or `**Answer (` of its own; see [run-model.md](run-model.md)), then appended to the end of the entry's one line as ` **Answer (human):** <text>`. The writer works on bytes: it splices that one line and keeps line endings, BOM, and other bytes as they were. It writes a temp file beside the queue, reads the queue again, and renames only if nothing changed. Results: `answered`, `changed` (entry gone, duplicated, or the file changed while saving), or `failed`.
- **Resolve (Close and Keep):** `POST /api/actions/resolve` with `repoId`, `line`, and `kind` (`close` or `keep`); any other field counts for nothing. The entry must be `isAnswerable` (`404 not waiting on you`), and the server's own `triage` of it must give a Done reason for `close` or a value for `keep` (`409` with `The board no longer reads this entry as done.` or `This entry states no value in use.`). The writer rewrites the line's `**Resolution:** pending` to `**Resolution:** <local date> — closed from the board: <reason>` or `— kept: <value>`, with the answer's path and guards; a line that no longer reads as pending is `changed`. It shares the answer's one write per repo (`409 answer in progress`). Results: `closed`, `kept`, `changed`, or `failed`, logged as `resolve` with the entry's header as the target.
- **Forget check** (`forgetCheck` in `packages/model/src/forget.ts`): whether a run may lose its port claim. Checks, first failure wins: the run isn't on `listRuns` for its repo → `not a run`; no claim names it → `no claim` (a plan doc's `Port base:` isn't a claim); its state is `running` → `run is running`; two or more claims name it, or it would still be listed with its claims taken out (a live plan) → `still listed`. Else `ok` with the one claim's port base. A leftover fix run (PR merged, agents ended) and a claimed archived plan closing out pass.
- **Where you press it:** Merge and Answer sit on the Next step card, or on a row in the Waiting tab, and open in place under it; the Action log is in the Log tab. Continue and Go sit on a reply ([runs-and-pipeline.md](runs-and-pipeline.md)).
- **Path:** exactly `<repo>/<stateDir>/handoff-queue.md`, whose real path must sit under the repo's real path. A missing file is never created. `stateDir` comes from the matched Board entry, never from the request: absent means `pod-docs`, else `.openaflow/workflows/<name>/state` ([run-model.md](run-model.md)). The writer refuses any other shape before a file call (`failed`, `bad state folder`). A line that is answerable in two entries (two state folders, or twice in one) is `changed` with `Two entries read the same. Answer it in the chat.`, and nothing is written; the request is logged.
- **Add repo's `openaflow` and `podDocs`:** `POST /api/repos` answers `201 { path, openaflow, podDocs }`. `openaflow` is true when `<repo>/.openaflow` exists as anything (`lstat`: a folder, a file, or a link, a broken one too), and also when the repo folder can't be read, so the page never offers a setup that can't work. `podDocs` is true when `<repo>/pod-docs` exists as anything, by the same rule, and also when the folder can't be read: setup hides a `pod-docs/` repo's runs, so the page sets up with no question only when both are false.
- **Set up** (`setup-routes.ts`, `POST /api/actions/setup-workflow { path }`): checks, first failure wins. `path` not a string or not absolute → `400 bad request`. Not a repo on the Board (by its own case rule) or in `config.json` (by `ignoresCase` of the listed path), with Add repo's identity rule → `404 not a repo`; the file system is asked only about registered paths, never the request's string, and the registered path is the one written to. A setup of the same repo already running → `409 setup in progress`. `<repo>/.openaflow` exists as anything → `409 already set up`. No bundle, or its template isn't a folder → `409 workflow missing`. Then it builds `<repo>/.openaflow.tmp-<hex>/workflows/claude-pod/` with `workflow.json` (`{ "source": "claude-pod", "version": "<bundled>" }`, 2-space JSON, final newline) and a copy of the template as `state/` (links copied as files), makes the template's empty folders in `state/` (`TEMPLATE_FOLDERS`: `plans`, `sprints/archive`, `ideas`, `known-issues`, `feature-details`, each with a `.gitkeep`; the packaged app's template has none of them, because electron-builder drops every `.gitkeep`), and renames it to `.openaflow`. A test checks the list against the built workflow's template. A `.openaflow` made during the copy is kept: the temp folder goes and the answer is `409 already set up`. Any failure removes the temp folder → `500 setup failed: <code>` (`unknown` when the error has none). Success → log, rebuild, then `200 { outcome: 'created', logged }`.
- **Use** (`POST /api/actions/use-workflow-version { repoId, name }`): the repo must be on the Board and `name` one of its `model.workflows` whose `source` is `claude-pod` (a workflow with no `source` doesn't count) → else `404 not a workflow`. No bundle → `409 workflow missing`. The file is `<repo>/.openaflow/workflows/<name>/workflow.json`, read fresh: missing, not a plain file, a real path outside the repo, bad JSON, or JSON that isn't an object → `409 workflow.json unreadable`. Same version → `409 already current`. It sets `version`, keeps every other key in its place, and writes 2-space JSON through a temp file beside the real file and a rename. A failed write removes the temp file → `500 update failed: <code>`. Success → log, rebuild, then `200 { outcome: 'updated', logged }`.
- **Action log:** one JSON line per logged request in `<config dir>/actions.jsonl`, never in a repo. Merge, answer, resolve, resume, remove-repo entries (`removed` or `failed`, the target is the repo's path), forget-run entries (`removed` or `failed`, the target is `<run> · port base <N>`), and the hosted-session entries ([hosted-sessions.md](hosted-sessions.md)): `new-session` and `resume-session` (`started` or `failed`) and `dismiss-session` (`dismissed` or `failed`), whose target is `<skill command or plain> · <marker first 8>` (a Resume's names the new marker), never the typed text; `setup-workflow` (`created` or `failed`, the target is `.openaflow/workflows/claude-pod · <bundled version>`) and `use-workflow-version` (`updated` or `failed`, the target is `.openaflow/workflows/<name> · <old version or no version> → <bundled version>`). Each pair is an `action` with its own results. Set up and Use log only an attempted write (`created`, `updated`, or a `500`'s `failed`), never a `4xx` refusal; a refused start (`409`, such as `run wrapper: …`) and a settings change write no entry; the reader drops lines that don't fit. `Board.actions` is the newest 50; after each logged action the server rebuilds the Board and sends it before it answers. A failed append gives `logged: false`.

## Why it's this way

- **`merged` only from the re-read** ([plan](../plans/board-actions.md#key-decisions)): gh's exit code doesn't say what happened; a timeout can still merge and a success can mean queued. Turned down: trusting the exit code.
- **`queued` only from a merge-queue entry:** gh 2.92's `pr view --json` has no merge-queue field, and an open PR after a successful call can also be a lagging re-read. Calling that `queued` would be false, so it reads `unconfirmed` (merge-actions wave 2 fix).
- **`--match-head-commit`:** merges only the commit you saw, so a push after the confirm (autopilot racing you, say) is refused as `stale`.
- **The board writes only the queue file, one answer line** ([plan](../plans/board-actions.md#key-decisions)): this changes phase 1's "never writes into a repo" rule as little as possible. Turned down: editing plans, sprint docs, or the entry body. Since default-workflow, setup's `.openaflow/` (after you agree) and Use's `version` line are the only other writes ([decision](../decisions.md#2026-11-23--openaflow-and-claude-pod-are-separate-workflows-live-in-openaflowworkflows-human)).
- **Setup builds in a temp folder, then renames:** a failure midway leaves no half `.openaflow`, which would mark the repo as set up and hide its `pod-docs/` runs. The in-memory lock is the only guard while the copy runs, because `.openaflow` doesn't exist yet.
- **Build answers before pod reads them** ([decision](../decisions.md#2026-10-21--build-queue-answers-before-pod-reads-them)): the board wrote the master plan's format first; claude-pod 0.8.0+ (claude-pod #96) now reads it at wave start and on resume, so the form says to answer here, then Continue, with no chat step. On a fix run or repo row it says the next `/pod:code` wave reads it instead, since `/pod:fix` reads no answers.
- **A write by pod wins:** the re-read before the rename turns a race into `changed` instead of losing pod's line.
- **Retry only on `EPERM` and `EBUSY`:** on Windows an editor or a scanner can hold the file for a moment; other codes won't pass on a retry.

## Watch out

- Tests and smoke runs never merge a real PR (a fake gh exec; the smoke recipe checks only refusals) and never answer a real repo's queue.
- In the GraphQL call, owner and name go with `-f` (raw); `-F` would turn `123` into a number or `@file` into a file read.
- Git Bash mangles `→` in command arguments: send an answer body from a UTF-8 file (`--data-binary @body.json`).
- The answer clears nothing: the entry stays `needs you` until pod reads the line and resolves it.
- A queue body can quote `**Answer (human):**` (pod's own gate entries do). Only a marker after the entry's `**Resolution:**` is an answer.
- `actions.jsonl` sits in the watched config folder, but the filter keeps only `config.json`, so the route rebuilds the Board itself.
- The rename gives the queue a default file mode. The log is read once at start and never trimmed.
- On POSIX, `rename` replaces an empty folder, so setup checks for `.openaflow` again just before the rename. The gap between that check and the rename is still open, but only an empty folder made in it would be lost.
- Forget also shows on a claim-only run whose open PR waits on your merge. It then takes the run and its PR off the board, and frees a port base a live session may still hold. Kept on purpose, because the modal asks first ([decision](../decisions.md#2026-11-13--forget-on-a-run-whose-pr-waits-on-your-merge-agent-default--override-anytime)).
